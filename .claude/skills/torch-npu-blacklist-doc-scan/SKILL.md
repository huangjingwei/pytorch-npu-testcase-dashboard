# NPU 屏蔽用例文档核验批量扫描

## 概述

输入一批失败的 PyTorch-NPU 测试用例（至少需要 nodeid + 报错日志，理想情况下还有 失败大类/torch-api/疑似CANN算子 等已有分类列），批量筛出其中能用**官方文档**（不是源码、不是报错文案本身）确认 dtype 或 memory_format 不支持、因此可以永久屏蔽的用例，产出一份三列汇总表：`nodeid | 对应算子 | 不支持类型`。

本 skill 提炼自一次对约 4000+ 条 NPU 失败用例做批量文档核验拉黑的实战经验（2026-10-08 至 10-10），踩过的坑和验证方法全部固化在 `references/` 里。

## 怎么调用本 skill——这是给 AI agent 读的方法论，不是一键脚本

**本 skill 的使用方式是把这个目录加进 AI agent（如 Claude Code）能读到的 skills 里，然后直接用自然语言让 AI"分析这批用例，找出能屏蔽的"——由 AI 读 `SKILL.md` 和 `references/`，对实际数据执行步骤 1-5，不是运行一个脚本从头跑到尾。**

几个容易误解、但必须澄清的点：

1. **步骤 1-4 没有脚本能做，必须是 AI/人工逐条判断**：筛候选要读报错日志、追踪真正失败的组件要查 `op_plugin_functions.yaml` 和源码调用链、文档核验要去对应仓库找版本匹配的官方文档逐条核对——这些都是需要理解和判断的分析工作，不是能喂进脚本自动跑完的。`scripts/generate_output_table.py` **只覆盖步骤 5（最后的格式化产出）**，如果指望"运行一下这个 skill"就能从原始失败日志直接吐出一张完整的屏蔽表，那是不会发生的——处理一批新用例，耗时和工作量基本等同于当初这 4000+ 条是怎么做出来的（见 `references/` 里记录的实际方法），不是秒出结果。
2. **不要求你的原始数据长成任何固定列结构**。步骤 5 的脚本按表头文字认列、不按固定位置，且 7 个候选列里只有 `nodeid` 是必须的（见步骤 5）——但这说的是 AI 自己在做完步骤 1-4 之后、为了调用格式化小工具而整理出来的**中间产物**，不是对你原始数据的要求。你的原始数据可以是任何列名、任何列序、任何来源，甚至就是"nodeid + 一段报错日志"这种最简单的两列，或者干脆是贴在对话里的一段文本——AI 应该先读懂你数据的实际结构，自己定位 nodeid/报错日志/已有分类在哪，而不是要求数据方先改格式来迁就脚本。
3. **步骤 5 的脚本本身是可选的，不是必经之路**。AI 做完步骤 1-4、手里已经有结论之后，既可以把结论整理成中间表丢给脚本格式化，也可以直接手写最终的三列 md——产出三列表这件事对 AI 来说本身就不难，脚本只是省得每次手写表格样式的小工具，不是流程里的硬性关卡。

## 何时使用

- 用户给了一批（通常是 Excel/CSV 形式）NPU 失败用例，问"哪些能屏蔽"
- 用户需要把"报错像是 dtype/格式问题"的一大堆 case 收敛成"文档确认不支持，可拉黑"的精确子集
- 用户要的交付物是一张 nodeid 对应算子/不支持类型的汇总表，不是逐条诊断报告

**不适用**：只有一条用例需要深入诊断根因、判断可修复性/优先级路由（需要一套更通用的"单条用例诊断"方法论，本 skill 不覆盖）；用户要的是修复代码（本 skill 只读，不改代码）；失败原因明显不是 dtype/memory_format（shape、编译、分布式、精度数值问题等——这些不在本 skill 范围）。

## 约束与边界

- **只筛查+核验+产出表格，不修改代码，不决定是否转 CANN 问题单**。
- **结论必须有官方文档出处（URL + 行号/小节），不能只凭报错文案下结论**。报错文案详实、甚至自带完整支持列表，都只是"初步信号"，不是终稿依据——详见 `references/dtype-doc-verification.md`。
- **源码（TORCH_CHECK/硬编码判断）不能替代文档**。如果报错栈追到的是 torch_npu 自己代码里的检查而不是 CANN/ACL 原生拒绝，必须先顺调用链找到真正执行计算的 CANN 算子，查**它自己**的文档，不能拿 torch_npu 源码当文档用。
- **文档说"支持"但运行时拒绝的，是矛盾案例，不进入屏蔽表**，要单独标记，不能当作"已确认不支持"处理。
- 疑似 dtype/memory_format 但查无版本匹配文档的，诚实标记"查无文档"，不强行凑一个结论。
- **查文档前先确认实际部署环境的 CANN/torch_npu 版本，核对版本匹配的 git 分支，不能用 `master`**——master 是未发布的未来版本，可能比部署版本多/少支持某些 dtype，用它核对会得出错误的"矛盾"或"确认"结论。这是全流程里最容易被跳过、后果也最严重的一步（错一次版本，一整批结论方向都可能反），详见 `references/dtype-doc-verification.md` 核验步骤第 2 条。**新一批用例的部署环境版本很可能跟做这 4000+ 条时用的 9.1.0-beta.3 不一样，不能假设版本没变就直接复用旧的分支/commit。**

## 完整流程

### 步骤 1：候选筛查——从全量失败用例里筛出 dtype/memory_format 候选

对数据集里每一行的**完整报错日志全文**做模式匹配，套用已知不支持模式的正则，筛出候选池。完整方法（含日志截断陷阱、"不要只看失败大类字段排除候选"的提醒）见 `references/candidate-screening.md`、`references/unsupported-patterns-excerpt.md`。

### 步骤 2：追踪真正失败的组件——测试表面现象 ≠ 真正失败的东西

这是批量扫描里最容易出系统性错误的一步。**候选用例里，报错提到的 dtype/算子，经常不是真正的根因所在**，必须先确认"这条用例到底是谁在失败"，再去查文档，否则查的是错的文档。torch-api 列/测试名只是"名义上在测什么"，不是"真正在算什么"；op_plugin 的 codegen 配置（`op_plugin_functions.yaml` 的 `gen_opapi: exec:` 字段）、调用栈里的 kernel 文件名，才是"真正调用了谁"的证据。

完整方法论（判断信号、反查真正组件的权威静态材料、内部命名黑名单、存在性校验、四个实测案例、批量处理常见误抓模式）见 `references/trace-to-real-component.md`，**本步骤务必通读该文件再执行，不要凭直觉判断**。

> 🔴 源码里的 TORCH_CHECK/硬编码限制不能当"已经找到真正的算子"的终点——报错没有 `AclNN_Parameter_Error`+`error code is 161002` 这种 ACL 原生格式时，必须继续往下追真正会被调用的 CANN 算子，不能止步于源码里的检查（svd_npu 反面教材，详见 `references/trace-to-real-component.md` 和 `references/dtype-doc-verification.md`"源码里的硬编码限制≠文档依据"一节）。

### 步骤 3：文档核验

确认了真正执行计算的 CANN 算子（或 torch_npu 官方 API）之后，完整走一遍 `references/dtype-doc-verification.md` 的核验步骤：版本匹配的文档分支、原地/非原地参数表的区分、独立列表与关系性约束都算数、报错层级判断。不在本文件重复，直接引用。

**两类结论都可能成立，不是只有"独立枚举列表"才算**：
- 某参数自己有固定的 dtype 清单，测的值不在里面 → 可屏蔽。
- 没有固定清单，但文档的"返回值/报错场景"表格（或参数的"使用说明"列）明确把这个具体的参数组合/场景列为错误条件 → 同样可屏蔽，不要因为"没有独立列表"就排除。

### 步骤 4：memory_format 类单独处理

如果候选落在"内存格式/布局限制"（`references/unsupported-patterns-excerpt.md` 类别 4），核验方式和 dtype 不同——查的是 torch_npu 自己的官方 API 文档（`docs/zh/api/native_api/.../torch-Tensor.md` 等，不是 CANN aclnn 文档），确认该接口的 `memory_format` 参数官方支持范围。确认后：

- "对应算子"列：填这个接口的 torch_npu 官方文档条目名（如涉及的是非 CANN 接口，如 `Tensor.npu()`/`TensorFactories`，就填这个名字，不要空着也不要塞一个不相关的 CANN 算子名）。
- "不支持类型"列：**统一直接写"非连续内存"**，不写具体的 `channels_last`/`channels_last_3d` 等细分格式名——这是本 skill 输出格式的明确约定。

### 步骤 5：产出三列汇总表

步骤 1-4 做完后，把结果整理成一张中间表，然后用 `scripts/generate_output_table.py` 产出最终的三列 md：

```bash
python scripts/generate_output_table.py <中间表.xlsx或.csv> <输出.md> --sheet Sheet1
```

中间表**按表头文字认列，不按固定位置，只要求有 `nodeid` 这一列**，其余 `失败大类 / torch-api / CANN算子 / 不支持类型 / 结论 / 文档链接` 全部可选、列序随意、可以有额外列——AI 分析完手里实际攒出了哪些信息，就给哪些列，不需要为了凑够 7 列而硬编一些空值。极端情况下中间表可以只有 `nodeid | 不支持类型` 两列。`结论` 列里对能"干净匹配"出真实算子名的行，按 `XXX文档支持类型：...` 这个格式写，供脚本识别。

脚本做的事：
- "对应算子"按步骤 2 的追踪优先级解析（有哪个信息源就用哪个，没有就跳过）：结论文本直接匹配 > 同一文档 URL 反推（处理表面现象≠真实组件但结论文本措辞不规整的行） > CANN算子列 > torch-api 列 > 都没有则标记未识别。
- "不支持类型"：有"失败大类"列且命中 memory_format 类别时统一写"非连续内存"（可用 `--memfmt-category` 自定义类别名）；否则取"不支持类型"列原始值，没这一列就标记未填写。
- 跑完会在 stderr 报告实际识别到了哪些列、哪些列没找到（不是报错，只是提示）、解析方式分布、"未能识别对应算子"的清单——**有未识别的行必须人工核实补全，不能让脚本自动留空直接交付**。

脚本只负责格式化产出这一步，不替你做步骤 1-4 的筛查/追踪/核验判断——那些步骤的结论质量直接决定这张表的质量，脚本本身不检查"结论是否真的有文档依据"。**这个脚本是可选的便利工具，不是必经关卡**：手里已经有干净的结论数据时，直接手写最终三列 md 完全可行，跑脚本只是省事；脚本报"表头不匹配"时不代表分析做不下去，调整一下中间表的整理方式，或者干脆跳过脚本即可。

矛盾案例、查无文档案例、步骤 2 没能定位到真正组件的案例，**不进中间表**，按 `templates/output-table.md` 里的两张附表单独记录，不要为了凑数塞进屏蔽表。

## 常见陷阱

- **不要只看"失败大类"字段的名字做候选筛查**：名字不带 dtype/内存字样的类别里可能藏着同样的根因（UInt 案例最初就不在直觉上像是 dtype 问题的类别里）。
- **不要把 torch-api 列当成"真正的算子"直接拿去查文档**：先走步骤 2。
- **不要把源码里的检查当文档**：没有 ACL 错误码格式的报错，必须继续往真正的 CANN 算子追。
- **不要因为"没有独立枚举列表"就排除关系性约束案例**：查文档的"返回值/报错场景"表格或参数"使用说明"列，很多关系性约束也是文档明确写出来的。
- **不要在文档说"支持"但运行时拒绝时下"确认不支持"结论**：这是矛盾案例，方向反了，不能进屏蔽表。
- **批量处理时不要依赖"第一次正则没命中就跳过"**：至少两种异常包装格式会把真正的报错行藏在常见截断点之后，见步骤 1 的陷阱提示。
