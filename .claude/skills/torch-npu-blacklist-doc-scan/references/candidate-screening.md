# 批量候选筛查

> 用于步骤 1：从全量失败用例里筛出 dtype/memory_format 候选，进入后续"追踪真正组件→文档核验"流程。

## 筛查方式

对数据集里**每一行的完整报错日志全文**（不是截断后的摘要，见下方陷阱）做模式匹配：

1. 套用 `unsupported-patterns-excerpt.md` 的**类别 1（dtype 不支持）**和**类别 4（内存格式/布局限制）**两组正则，命中其一即列为候选。
2. 对"失败大类"这一列（如果数据集里有现成分类）里**名字本身带 dtype/内存/格式字样**的类别（如"dtype不支持"、"dtype不匹配"、"内存格式错误"），即使具体某一行报错文案没有直接命中正则，也应该整类纳入候选池复查——命中正则但措辞特殊是常见情况，正则覆盖的格式目录在 `dtype-doc-verification.md`"报错文案格式速查"一节里持续扩充，不会一次性穷尽。
3. **不要只看"失败大类"字段的名字就排除候选**。类别字段是分类时的产物，不是因果判断。实测过候选命中跟字面"dtype"无关的类别（UInt16/32/64 相关失败最初归在跟 dtype 看似无关的功能测试类别里，根因其实是测试样本构造阶段的随机数生成算子不支持该 dtype，见 `trace-to-real-component.md`）。如果数据规模允许，建议对**全部**失败大类做一次低成本的正则扫描，而不是只扫"名字像 dtype"的那几类。

## 陷阱：日志截断导致候选漏判

批量提取报错特征时，永远对**完整原始日志全文**搜索，不要用"找到某个标志字符串就截断"的简化逻辑——`Exception: Original OpInfo is broken` 和 `The Inner error is reported as above...` 这两种异常包装会把真正的 CANN 报错行放在常见截断点**之后**。一次实测里，986 条用例因为这类截断被误判"无信号"，全文重扫后 391 条其实有完整支持列表。

如果第一轮正则没有命中，不要立即判定"无信号"，换一个更宽的关键词网（`dtype`、`DT_`、`数据类型`、`not support`、`not implement`、`supported list`、`promot`、`Complex`/`COMPLEX`、`Data Type:`）重新扫一遍全文，排除掉 `SampleInput(...)`/`Tensor[size=...]` 这类纯数据回显行的噪音后再确认是否真的没有信号。

详见 `dtype-doc-verification.md`"日志截断陷阱"一节。
